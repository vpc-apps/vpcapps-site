Go/No-Go Release Scorecard for Jira

Know if this release can ship, with the reasons. The app reads a release’s defects in your Jira project and shows GO, AT RISK, NO-GO or NO DATA. It works on Jira Cloud.

Contents: Set up · Team-managed spaces · How verdicts work · Rules, templates and views · Compared with the previous release · Print and share · Dashboard gadget · Troubleshooting · Your data · Support

Set up

  1. A Jira admin installs the app from the Atlassian Marketplace.
  2. Open your project. Go/No-Go Release Scorecard appears as a tab in the project’s navigation (in some layouts under Apps or the + next to the tabs).
  3. Pick a release. The first one offered is the next unreleased release.

For a useful result, your project needs:

NeededWhy
An issue type with “Bug” or “Defect” in its nameOnly these are scored
At least one releaseThe picker lists your project’s releases
Fix versions set on defectsThis links a defect to a release
Priority on defectsThe two priority rules read it
Affects versions on defects (optional)Used for “found in the last release after it shipped”

Company-managed projects usually have Fix versions and Priority on the Bug screen already.

Team-managed spaces

A new team-managed space shows neither Fix versions nor Priority on a Bug. Two steps fix this:

Add Fix versions: click the + next to the space tabs, choose Releases, then Add to navigation. The Fix versions field then appears on your work items.

Add Priority: go to Space settings → Work types → Bug, click Priority, then Save changes.

Team-managed layouts do not offer Affects versions, so “found after it shipped” stays empty there. It is for information and does not change the verdict. In a team-managed space the app shows a short setup box with only the steps your report needs; it is left out of prints and downloads.

How verdicts work

Each rule compares a number with two limits: at or below GO it passes; above GO but at or below AT RISK it is at risk; above AT RISK it fails. The overall verdict is the worst result of any rule. If no defects are linked to the release, the verdict is NO DATA, never GO.

Default limits:

RuleHow it is countedGO at or belowAT RISK at or below
Open blocker / critical defectsOpen defects with priority Highest, Blocker, Critical, Urgent, Showstopper or P000
Open high-priority defectsOpen defects with priority High, Major or P125
Reopen rateShare of the release’s defects moved from a done status back to a not-done status at least once10%20%
Defects open more than 30 daysOpen defects created over 30 days ago310
Created minus resolved, last 14 daysDefects in this release created, minus those resolved, in the last 14 days05
Open defects without steps or attachmentShare of open defects with no attachment and no description text such as “steps to reproduce”, “expected result” or “actual result”25%100%
  • “Open” means the status is not in Jira’s Done category.
  • The four count rules can instead be set as a % of all defects in the release (“Count as” in the rules editor, 0–100). Reopen rate and the evidence rule are always percentages.
  • Priorities with other names, such as “P2”, are not counted by the priority rules. Description text is matched in English only.
  • The app reads the first 2,000 defects of a release; above that the report says partial data.

The verdict supports your decision; it does not replace it. It reflects only what is recorded in Jira and does not read test runs or test cases.

Rules, templates and views

Changing the limits. Project admins and Jira admins see Edit rules. Change the numbers (whole numbers; each AT RISK limit at or above its GO limit) and click Save rules. Limits are kept per project and apply to everyone viewing that project. The report then says the verdict was recalculated and highlights the checks whose result changed. Use defaults restores the Standard limits. Everyone else sees View rules, read-only. The rules card says whether the report uses limits set for this project or the defaults.

Criteria templates. In the rules editor, start from a template, then adjust; nothing is saved until you click Save rules.

TemplateForIn short
StrictRegulated or enterprise releasesNo open critical or high defects, nothing left open for 30 days, a low reopen rate
StandardMost teamsThe built-in defaults in the table above
Fast-movingStartups and internal toolsLimits as a share of all defects, more room for open work; only critical defects block

Report views. The View menu chooses which reports you see, print in full and download:

ViewShows
ExecutiveThe verdict, a card per rule, the comparison with the previous release, the trend and open blocker defects
QA leadEverything: all charts and tables
Release managerThe comparison, priority mix, carried-over defects, defects found after the last release shipped, status by priority, age and assignee

Compared with the previous release

When the project has a previous released release (marked released, with a release date) that has defects, the report adds:

  • Change cards: defects, highest/critical, high, reopen rate and median days to fix, with green (better) or red (worse) arrows. Lower is better on every card; rate changes are in percentage points.
  • Priority mix: this release and the previous one side by side.
  • Carried over: defects of this release that are also set to the previous release, or were moved out of it (from the Fix version history). Shown only when there are any.

With no previous release, or one without defects, the comparison is left out rather than showing empty numbers. It is on screen and in the download, not on the one-page print.

Print and share

  • Print summary (1 page): the verdict, one card per rule and the key charts on one A4 page, readable in black and white.
  • Print full report: every chart and table of the chosen view, over several pages.
  • Download shareable report: one HTML file with no scripts, for people without Jira access.

Use the app’s own buttons. The browser’s Print menu, or Ctrl+P while the focus is on Jira’s page, may come out blank, because the app sits in a frame inside the Jira page. Pressing Ctrl+P after clicking inside the app prints the summary.

Printed and downloaded reports contain defect keys, summaries, priorities and assignee names. Treat them as you would any Jira export.

Dashboard gadget

  1. On a Jira dashboard, choose Add gadget and find Go/No-Go Release Scorecard.
  2. In its settings, enter a project key, such as WEB, and optionally a release (empty means the next unreleased one) and a view.

Troubleshooting

You seeWhat to do
No defects are linked to this release (NO DATA)Check the defects use Fix versions with this exact release. In a team-managed space, add the Releases view first
This project has no releases yetAdd a release, set it as Fix versions on the defects, and come back
This project has no issue type named Bug or DefectThe app only scores those types. Add one, or rename yours if that suits your project
Priority rules show 0 but you have urgent defectsAdd Priority to the Bug type (above), and check your priority names against the rules table
“Found after it shipped” is always emptySet Affects versions on defects, and check the previous release is marked released with a release date. Team-managed spaces do not offer this field
No comparison with the previous releaseShown only when there is a previous released release with a release date that has defects
Partial dataThe release has over 2,000 defects, so only the first 2,000 were read
Could not read this from JiraThe message gives the reason. The app sees only what you can see, so ask for access if needed. If Jira is busy, wait a minute and reload
Only project admins and Jira admins can change these rulesAsk one of them to change the limit
The saved go/no-go rules could not be loadedThe verdict uses the defaults for now. Reload to try again. Editing is off until they load, so saved limits cannot be overwritten
Could not save the rulesThe app already tried twice. Nothing changed; try again in a moment
The licence for this site is not activeA Jira admin can renew it under Apps
The print comes out blankUse the app’s own Print summary or Print full report button
Age numbers look wrongThey are based on Jira’s created and resolved dates; imported defects may carry their import date

Your data

  • The app reads issues in your browser, with your own Jira permissions, through Atlassian’s platform. Nothing goes to VPC Apps or any other outside service.
  • It stores only what an admin sets for a project: the rule limits, how each rule is counted and the template it came from, in Atlassian’s Forge storage for your site. No issue data and no personal data is stored.
  • To check who may edit limits, the app asks Jira for the viewer’s own project permissions, on Atlassian’s platform. The answer is not stored.
  • In-scope End-User Data for data residency: the saved rule settings and the project ID they belong to, in Forge hosted storage, which follows your Jira site’s location. Out of scope: nothing else is stored; issue data is read at viewing time and not kept.
  • After you uninstall, Atlassian’s Forge storage keeps the app’s data for 28 days, then removes it.
  • This documentation page, like the rest of vpcapps.net, counts anonymous visits with Cloudflare Web Analytics (no cookies). The app inside Jira has no visit counter.
